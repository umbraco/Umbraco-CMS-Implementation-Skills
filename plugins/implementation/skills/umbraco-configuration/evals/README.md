# Running these evals

All five evals in `evals.json` are meant to run together, with and without the skill, using the
`umbraco-skill-evaluator` skill. They need a small project to work in; without one, the baseline
has no schema to consult and nothing to edit, and the results are not comparable.

## Project fixture (every eval, both sides)

Give each run its own sandbox laid out like this:

```
<run>/outputs/
  Directory.Packages.props     # copy of the repo-root file — see "Outside-the-project check"
  project/                     # the "user's project": the agent edits here, in place
    Program.cs
    Umbraco-CMS.Skills.csproj
    appsettings.json
    appsettings.Development.json
    appsettings-schema.json
    appsettings-schema.Umbraco.Cms.json
```

Copy the six project files from `Umbraco-CMS.Skills/` in this repo. Build that project first: the
two schema files are generated by the build and are not committed.

Then overlay the eval's own `files` (paths relative to the skill root) onto `project/`, replacing
any file of the same name. Every eval has one, an `appsettings.json`:

- Evals 2 to 5 use `files/project/appsettings.json`, the reference site's file without its
  `Imaging` block. That block carries a fake HMAC key and a long explanatory comment that exist
  only for the reference site; left in, runs spend their reply discussing it.
- Eval 1 uses `files/single-server/appsettings.json`, which adds a SQL Server connection string and
  `ModelsMode: InMemoryAuto`, the starting state its prompt describes. The password in it is a
  fixture value, not a secret.

## Run prompt

Tell each run where the project is and to edit it in place, to save its reply to
`outputs/answer.md` and a transcript to `transcript.md`, and that it may fetch public docs. Give the
with-skill run the path of a **snapshot** of the skill that contains only `SKILL.md`, `references/`
and `assets/` — not the skill folder itself. `evals/` holds the expectations and `examples/` holds
the tests, and a run that can reach them will read them (an instruction not to is not enough; it
has been ignored). Tell the baseline run not to read `plugins/`, `.claude/` or any
Umbraco source checkout, or it will find the skill by browsing.

Do not tell either side to avoid writing outside the project: that is one of the expectations.

## Outside-the-project check

`dotnet add package` in a centrally-managed project edits the nearest `Directory.Packages.props`
above it. The copy in `outputs/` is there to absorb that, so the repo's own file is never touched.
After a run, compare the copy with the original; a difference fails the "does not create or modify
any file outside the user's project folder" expectation.

## Reviewing in the viewer

The evaluator's viewer lists only the files directly inside `outputs/`, not those under
`outputs/project/`. Before generating the report, copy each file the run created or changed up into
`outputs/` (for example as `changed - Program.cs`), or a reviewer sees only `answer.md` and will
think the code changes are missing.

## Grading notes

- Eval 4 is advice-only. Grade it from `answer.md`.
- Eval 5: the unmodified `appsettings-schema.Umbraco.Cms.json` contains a `DistributedJobSettings`
  key under `UmbracoCmsDefinition`. If that key has been renamed, the run edited the schema.
- A conditional expectation whose condition never arises (for example the `ModelsMode` check when no
  server is set to Production mode) is not applicable; do not grade it as a fail.
